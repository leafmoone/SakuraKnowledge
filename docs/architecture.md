# Architecture / implemented boundary

`model.py`: frozen keys, evidence statuses, fixed image groups and version-2 NFKC/casefold tokenization (Latin words, overlapping CJK bigrams, without 256-token truncation on documents). `storage.py`: normalized JSONL importer from private SHA-checked frozen byte copies, SQLite foreign keys, per-record savepoints, bounded disk-based duplicate tracking, order-independent link staging, and no-replace publication. `api.py`: shared offline read-only query layer. `cli.py`: JSON command boundary and opt-in latest metadata fetch. `safety.py`: digest-checked ZIP extraction into a new directory. `mapping.py`: candidate cardinality/missing/reverse-consistency audit only.

SQLite tables: sources, entries, entry_evidence, aliases, documents, occurrences, links, source_counts, build_meta, search_fts. Each entry-version/alias/document/link has independent evidence. Original entry metadata (excluding separately stored aliases/documents/occurrences) survives in entry_evidence.payload: a body refresh does not rewrite an older mapping date. Divergent type/locator metadata quarantines a key; a duplicate normalized record remains accounted for without promotion. New revisions must receive distinct source_id values. Snapshot identity hashes manifest bytes. Queries use mode=ro, immutable=1, query_only and a five-second SQLite progress deadline; only closed, published snapshots may be read. WAL is checkpointed before publication. The sibling directory is renamed with no-replace semantics after integrity, foreign-key, FTS coverage, ledger and input digest checks.

Remaining gaps: normalized fixtures are not real adapters or proof of source fidelity; manifest inventory typing and source-declared expected-count semantics require audited input schemas. Rejections are recorded in a bounded sibling receipt (first 100), and any rejected/unresolved input blocks publication. Query search scans at most 10,001 ranked documents after SQLite work is bounded by the progress handler; LIMIT alone does not bound BM25 sorting effort. Verification checks FTS coverage/content row alignment, not a read-only FTS5 internal token-index audit; the write-side build executes FTS5 integrity-check. This is an engine baseline, not full P1 acceptance.
